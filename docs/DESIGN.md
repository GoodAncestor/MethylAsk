# MethylAsk — System Design

*A web tool that reads a person's methylation/epigenomic file, matches the markers against public scientific databases, and produces a readable report of what is known about them. Runs on a local server or private cloud so that personal data stays under the operator's control.*

This document proposes an architecture and explains the reasoning behind each choice. It is written for a moderately technical reader: you should be comfortable with the idea of files, databases, and web servers, but you do not need to be a bioinformatician.

---

## 1. What the tool has to do

A user hands MethylAsk a file. The file contains, for hundreds of thousands of positions in the genome, a number describing how methylated that position is (methylation is a chemical mark on DNA that turns genes up or down; the number is usually a fraction from 0 to 1). MethylAsk then needs to answer, position by position: **what is known about this mark?**

That breaks into four jobs:

1. **Read** the file, whatever vendor format it arrives in.
2. **Normalize** every marker to a common coordinate system, because the same position is named differently across array generations and genome builds.
3. **Interpret** each marker by looking it up in reference databases — disease associations, cancer patterns, aging clocks, regulatory context.
4. **Report** the findings, either in a live web page the user can explore or as a static file (HTML or PDF) generated by a script.

The design below is organized as a pipeline that mirrors those four jobs, plus a data layer that feeds job 3.

## 2. Architecture at a glance

```
                          ┌─────────────────────────────────────────────┐
                          │                MethylAsk                     │
                          │                                              │
  user file  ──────────►  │  [1] Ingest ──► [2] Normalize ──► [3] Annotate ──► [4] Report │
  (.idat / .csv / .bed)   │       parsers        liftover /        lookups        HTML/PDF │
                          │                      probe mapping         │                    │
                          │                                            ▼                    │
                          │                                   ┌──────────────────┐          │
                          │                                   │   Data layer     │          │
                          │                                   │  cache-first,    │          │
                          │                                   │  API-on-miss     │          │
                          │                                   └────────┬─────────┘          │
                          └────────────────────────────────────────────┼────────────────────┘
                                                                        │
                              local cache (bundled + synced)            │      remote APIs
                              ┌───────────────────────────────┐        │   ┌───────────────────┐
                              │ manifests, EWAS dump, clock    │◄───────┴──►│ EWAS Atlas, GDC,   │
                              │ coefficients, ClinVar snapshot │  refresh   │ ENCODE, OpenGWAS   │
                              └───────────────────────────────┘   job      └───────────────────┘
```

The important structural idea: **the pipeline never talks to the internet directly.** It asks the data layer a question ("what is known about cg00000029?"), and the data layer decides whether to answer from local cache or reach out to a remote API. Everything above the data layer is the same whether the tool is online or fully air-gapped.

## 3. The data layer (the part worth getting right)

You asked for a program that supports both a local cache and live APIs, and that keeps up with changes. That combination is the core of the design, so it gets its own section.

### 3.1 A single interface, several backends

Every reference database sits behind one common interface — a **provider**. A provider knows how to answer a small set of questions (lookup by CpG probe, by gene, by genomic position, by trait) and hides where the answer comes from. Concretely, each provider implements the same three methods:

- `get(key)` — return what is known about one marker
- `refresh()` — update the local copy from source
- `status()` — report version, date fetched, and record count

The annotation step (job 3) only ever calls `get()`. It does not know or care whether the answer came from a file on disk or an HTTP request. This is what lets the same codebase run interactively online and as an offline batch script.

### 3.2 Three backend types

Providers come in three flavors, chosen per database based on how that database is actually distributed (from the formats research):

| Backend type | When used | Behavior |
|---|---|---|
| **Bundled** | Data is static and small enough to ship | Loaded from a file that comes with the install. Example: Illumina + Zhou-lab manifests, epigenetic clock coefficients. |
| **Synced cache** | Data is downloadable in bulk and updates periodically | A local copy (SQLite or Parquet) built by a refresh job, queried locally at runtime. Example: EWAS Catalog dump, ClinVar snapshot, a slice of TCGA. |
| **Live-through cache** | Data is large, changes often, or is API-only | Queried from the remote API on a cache miss; the result is written to the local cache with a time-to-live, so the second lookup is local. Example: EWAS Atlas REST, GDC, ENCODE, OpenGWAS. |

The live-through type is what reconciles "cache everything" with "keep up with changes." A marker is fetched from the API the first time anyone asks about it, then served from cache until its time-to-live expires. Popular markers cost one API call ever; the cache fills itself with the markers people actually look at.

### 3.3 Keeping up with changes

Two mechanisms, so the operator can pick per database:

1. **Scheduled refresh.** A `methylask refresh` command (run by cron or a container schedule) rebuilds the synced caches from source and records the version and date. This is the right model for the big curated dumps that publish a new release a few times a year — EWAS Catalog, ClinVar, manifests.
2. **Time-to-live expiry.** Live-through caches carry an age limit per record. When a cached answer is older than its limit, the next lookup refetches it. This suits resources that change continuously and have no clean "release."

A `methylask status` command prints every provider's version and cache age, so the operator can see at a glance how stale the local picture is. Reports also carry a footer listing the database versions used, so a report is reproducible: you can tell exactly which snapshot produced it.

### 3.4 What to bundle vs. fetch — with measured sizes

The split below uses download sizes measured live during validation (see the validation doc). **Storage capacity is not a constraint anywhere** — the full set, including the 294 GB GDC corpus, fits on a normal NVMe drive on the hosting server. So the split is not about where there is room; it is about one hard limit and one soft preference:

- **The one hard limit is GitHub's 100 MB per-file cap.** Files above it cannot be committed to the repo without Git LFS. That is the only reason a file is *not* in the repo.
- **The soft preference is keeping the repo lean and clone-able** — so even some sub-100 MB but frequently-rebuilt data is better left on disk than versioned in git.

Everything not in the repo simply lives on the **server's local NVMe** (the 80 TB NAS is available for backup/mirroring but is not needed for capacity):

- **Ship in the GitHub repo** (each ≤~100 MB, static): Zhou-lab manifests (HM450 22 MB, EPIC 37 MB, EPICv2 39 MB), epigenetic clock coefficients, EWAS Catalog studies metadata (0.3 MB), a curated marker → plain-language annotation table. Normal committed files.
- **Synced cache on server disk** (rebuilt on release): EWAS Catalog full results dump (174 MB), ClinVar GRCh38 VCF (193 MB, weekly), dbSNP common-variant subset, OpenGWAS trait dumps, reference normal-tissue β ranges. Over the git single-file limit or updated too often to version in git.
- **Full local mirror on server disk** (large but fits on NVMe): GDC/TCGA cancer methylation (**294 GB across 20,397 files**). With a 10 Gbit connection the whole corpus downloads in well under an hour (the limit is per-file API overhead across 20k files, not bandwidth), so the simplest correct choice for the prototype is a **full local mirror** rather than on-demand caching. The live-through mode still exists for sources that genuinely change, but for a static research snapshot like GDC, mirror-and-be-done removes first-run latency and a class of cache-miss bugs.

Because neither storage nor bandwidth is a constraint here, the default posture flips: **mirror by default, use live-through only where freshness matters** (e.g. ClinVar's weekly updates). The operator can still switch any provider to live-through with a config flag — the interface does not change.

## 4. The pipeline stages

### 4.1 Ingest

A set of parsers, one per input format, each producing the same internal object: a table of `(marker_id, value, detection_confidence)` plus a metadata header (array type or sequencing platform, genome build, sample info). Priority order for what to support, matching where real files come from:

1. **β-value / M-value matrix** (CSV/TSV) and **GEO series matrix** — most third-party and public exports; simplest, ship first.
2. **Raw Illumina IDAT** pairs — the true raw array output; parsed with an established library rather than hand-rolled.
3. **bedMethyl / Bismark coverage** — sequencing-based methylation.
4. **modBAM and bigWig** — long-read and track formats; a later phase.

Each parser is small and independently testable, and adding a new vendor format later means adding one parser, not touching the rest of the pipeline.

### 4.2 Normalize

The stage that prevents wrong answers. The same physical position on the genome is called `cg00000029` on one array, carries a replicate suffix like `cg00000029_TC21` on EPICv2, and sits at different coordinates under genome build hg19 versus hg38. Before any database lookup, every marker is resolved to a canonical `(probe_id, chrom:position, build)` triple. This uses the bundled manifests plus published cross-platform conversion tables (SeSAMe `mLiftOver` / Zhou-lab maps). A marker that cannot be confidently mapped is flagged and excluded from interpretation rather than guessed at — a wrong genomic position produces a confidently wrong clinical statement, which is the failure mode most worth avoiding.

### 4.3 Annotate

For each normalized marker, the annotation engine calls the data-layer providers and assembles the findings: disease/trait associations (EWAS), cancer-pattern context, regulatory role, gene mapping, and any variant-level clinical note for the SNP probes on the array. Aging clocks are computed here too — locally, from published coefficients, so no β-values leave the server. Every finding is stamped with an **evidence tier** (§4.3.1) and a **category** (§4.3.2) so the report can present the broadest possible set of associations while making the strength and type of each one explicit.

#### 4.3.1 Evidence tiers

The goal is breadth: include as many relevant associations as the databases support, and let the reader see how much weight each one carries. Every finding gets one of four tiers, computed from fields the sources already return (study count, sample size, replication, p-value, curation status):

| Tier | Meaning | Rough criteria |
|---|---|---|
| **Robust** | Replicated across independent studies or large curated cohorts | Multiple studies or a large n, consistent direction, genome-wide significance, or a curated clinical classification |
| **Moderate** | Real signal, limited replication | Single well-powered study, or several small ones agreeing |
| **Speculative** | Preliminary or weak | One small study, borderline significance, or unreplicated |
| **Unknown** | Marker is on the array but nothing is recorded for it | No hits in any provider |

The tier is stored as data, not prose, so the interactive view can filter on it and the static report can group by it. Every finding also carries the source name, study identifiers (PMID), and a deep link back to the originating record so a reader can go verify it themselves.

#### 4.3.2 Categories — clinical and popular-interest side by side

MethylAsk targets an open, unregulated audience but does not exclude clinical relevance. Findings are tagged into categories so both kinds of interest are served from the same engine:

- **Clinical-relevant** — disease associations, cancer methylation patterns, pharmacogenomic markers, variant classifications. Presented as *research associations with an evidence tier*, never as diagnoses (see §5, disclaimers).
- **Aging & wellness** — epigenetic clocks, smoking/lifestyle exposure signatures.
- **Traits & ancestry** — the 23andMe-style popular-interest layer: benign trait associations, tissue-of-origin signals, and other findings people enjoy exploring.

A finding can hold more than one category. The report lets the reader move between "show me everything with clinical relevance" and "show me the fun stuff" without running a different analysis.

#### 4.3.3 Error-tolerant providers

A source that is unreachable or returns an error is **not dropped from the design or the report**. Each provider's `status()` records its state — `ok`, `stale`, or `unavailable: <reason>` — and the annotation engine proceeds with whatever providers are healthy. Where a provider is down, the affected section of the report shows a short note ("EWAS Atlas unavailable at generation time: upstream 502 — retry scheduled") instead of silently omitting it, and a scheduled retry brings it back automatically. This is why the two sources that were down during validation (EWAS Atlas, OpenGWAS) remain first-class providers in the registry.

### 4.4 Report

Two output paths off the same assembled findings:

- **Interactive:** a web page where the user searches markers, filters by category (aging, disease risk, pharmacogenomics, ancestry-neutral traits), and drills into the evidence behind each statement.
- **Static:** a `methylask report sample.csv --pdf` command that renders the same findings to a self-contained HTML or PDF file. Useful for handing a person their results, for archiving, or for running with no browser involved.

Both paths draw from one report model and one set of templates, so the interactive view and the printed document never drift apart.

## 5. Disclaimers — one place, not scattered

Per the project's intent — an open, unregulated tool that keeps clinical relevance but makes no definitive health claims — disclaimer language lives in **exactly one place** and is referenced from everywhere else. It is not repeated across code comments, UX copy, or per-section footers.

**Where it lives:** a single `DISCLAIMER.md` (source of truth). The web UI links to it from one persistent footer link; the static report embeds it once as a final "About these results" page; the CLI prints a one-line pointer to it. Code comments do not restate it — at most they carry a one-line `# see DISCLAIMER.md` where a reader might otherwise wonder.

**What it says (the substance, kept concrete):**
- MethylAsk reports **research associations** between methylation markers and traits or conditions, drawn from public scientific databases. It does not diagnose, treat, or predict disease.
- Each finding carries an **evidence tier** (robust / moderate / speculative / unknown). A tier is a description of how much scientific support exists, not a statement about the reader's health.
- Associations are population-level and often tissue- and ancestry-specific. A marker being present does not mean an outcome will occur.
- Results are **not a substitute for professional medical advice**. Anyone considering a health decision should consult a qualified clinician who can see their full context.
- The underlying databases are updated over time; a report reflects the database versions recorded in its footer at generation time.

**What the design does so the disclaimer can stay minimal:** the evidence tier and the "research association, not diagnosis" framing are built into the data model and the report layout, so the interface carries the caution structurally (a speculative finding *looks* speculative) rather than through repeated warning text. This is what lets one short disclaimer section do the whole job.

## 6. Two run modes, one codebase

You framed the choice as interactive versus a script that regenerates static content. The design supports both without forking, because everything below the report stage is identical:

- **Interactive service:** a web server (the pipeline behind an HTTP API, a front-end on top). The user uploads a file and explores results live. Good for exploration and for operators who want a hosted tool on their private cloud.
- **Batch script:** a command-line entry point that runs ingest → normalize → annotate → report and writes an HTML/PDF file. Good for automation, for air-gapped environments, and for generating a fixed deliverable per sample.

A reasonable path is to build the pipeline and the batch script first (it is the smaller, more testable surface and it exercises the whole data layer), then wrap the interactive service around the same core once the pipeline is solid.

## 7. Deployment and privacy

Because the input is personal genomic data, the design keeps computation local by default:

- **Ships as a container.** One image containing the code plus the bundled data; the synced caches mount as a data volume so they persist across upgrades and can be pre-populated. Runs the same on a laptop, an on-prem server, or a private-cloud VM.
- **Egress is limited to the data layer.** Only the live-through providers make outbound calls, and only for reference lookups by marker ID — never the user's values. An operator who wants zero egress promotes every provider to a synced cache and runs fully offline.
- **User data is not persisted by default.** A processed file lives in memory for the duration of a run; the report is the only durable output, and it is written wherever the operator chooses.
- **Reproducibility footer.** Every report records the tool version and the version of each database used, so a result can be regenerated and audited later.

## 8. Compute profile — what is light and what is not

Short answer: **per-sample runtime is light** — it is dominated by lookups and two small arithmetic steps, and a dedicated small server compartment is ample. But three things are worth stating precisely so the sizing is not based on the wrong mental model.

### 8.1 The light parts (your instinct is correct)

- **Per-marker lookups.** An array has ~935K probes. Against properly indexed local tables (SQLite/Parquet keyed by probe ID) this is hundreds of thousands of point lookups — sub-second to a few seconds per sample, kilobytes of working memory. This is the bulk of what the tool does.
- **Epigenetic clocks.** Each clock is a weighted sum over a few hundred CpGs (Horvath = 353, Hannum = 71). That is a dot product — microseconds. Running every clock on a sample is still trivial.
- **A processed β-value vector is small.** 935K probes × 8 bytes ≈ 7.5 MB per sample in memory. Even hundreds of samples fit in RAM easily.

So the interactive/report path for a single user is genuinely low-load. A modest compartment (a few cores, 8–16 GB RAM) handles it with room to spare.

### 8.2 The one heavy step — and it runs once, not per sample

Making the 294 GB GDC/TCGA corpus *useful for lookup* means precomputing per-CpG summary statistics: for each probe, the methylation distribution in tumour vs normal tissue for each of ~33 cancer projects. That is a single streaming pass over 294 GB across 20,397 files.

- **Cost:** I/O-bound, minutes to about an hour depending on disk and parallelism; memory stays modest if streamed (tens of MB, not the whole corpus at once) or benefits from more cores if parallelized.
- **Output is tiny:** ~935K CpGs × ~33 projects × a few statistics ≈ a few hundred MB, which then serves fast lookups forever.
- **Frequency:** once per data release. It belongs in the `refresh` job, not the request path. Users never trigger it.

This is the one place worth giving cores to, and only during a refresh.

### 8.3 The distinction that avoids a trap — "format conversion" vs "normalization"

Converting an *already-processed* β-value file between layouts (CSV ↔ GEO matrix ↔ internal table) is trivial and low-load, as you expect. But going from **raw IDAT → β-values is not a format conversion — it is normalization**, and it is a real analytical step:

- It involves background correction, dye-bias correction, and detection-p-value filtering. Different choices produce different β-values, which in turn shift epigenetic clock ages by real amounts.
- It should use an established library (SeSAMe / minfi in R, methylprep in Python), never a hand-rolled parser, because those encode the correct chemistry.
- **Per single sample it is still light** — seconds to a couple of minutes, a few hundred MB of RAM. The cost only grows if you batch many samples at once (minfi's multi-sample objects can reach tens of GB across hundreds of samples), which is not the consumer path.

The practical rule: treat "convert my already-processed CSV" as trivial, but treat "read my raw IDATs" as a normalization step that pulls in a real dependency and a documented set of choices.

### 8.4 Sizing recommendation

| Workload | Resource | When |
|---|---|---|
| Per-sample report (lookup + clocks) | 2–4 cores, 8–16 GB RAM | Every request — light |
| Raw IDAT normalization (single sample) | +a few hundred MB RAM, seconds | Only when a user uploads raw IDATs |
| GDC index build | More cores help (parallel I/O), ~an hour, modest RAM | Once per data release, in `refresh` |
| Disk | NVMe with ~400 GB free (294 GB GDC + the rest + headroom) | Static |

A single dedicated compartment sized for the middle rows, with the refresh job allowed to use more cores transiently, covers everything. There is no sustained heavy-compute component and no GPU need.

## 9. Suggested technology

These are defaults, not requirements; the architecture does not depend on them.

| Concern | Suggestion | Reason |
|---|---|---|
| Pipeline language | Python | The methylation parsing ecosystem (methylprep, pandas, pysam) lives here; array-parsing gaps can call out to R (minfi/SeSAMe) via a thin bridge. |
| Local cache store | SQLite + Parquet | SQLite for keyed lookups (marker → annotation), Parquet for the large columnar dumps. Both are file-based, no separate database server to operate. |
| Web service | FastAPI | Turns the same pipeline functions into an HTTP API with little extra code. |
| Report rendering | HTML templates → PDF via a headless renderer | One template set feeds both the interactive view and the static file. |
| Packaging | Docker/OCI container | Uniform deployment across local server and private cloud. |
| Refresh orchestration | A `refresh` CLI command driven by cron or a scheduled container job | Keeps caches current without a always-on scheduler service. |

## 10. A staged build order

1. **Data layer + two providers.** Build the provider interface and the cache, wired to one bundled source (Zhou-lab manifest) and one working live source (EWAS Catalog — validated returning real per-CpG associations). This de-risks the hardest part first. EWAS Atlas and OpenGWAS register alongside them as error-tolerant providers, so the retry path is exercised from day one.
2. **Ingest + normalize for β-value CSV.** Get one real file all the way to canonical markers.
3. **Annotate + static report.** Produce a first PDF from a real sample end to end.
4. **Epigenetic clocks.** A visible, self-contained feature that runs fully locally.
5. **More parsers (IDAT, bedMethyl) and more providers** (GDC, ClinVar, ENCODE).
6. **Interactive web service** wrapped around the working pipeline.
7. **Scheduled refresh + status reporting** to keep the caches current in production.

## 11. Open questions to settle next

Settled this round: run modes (both, one codebase), evidence tiering (4 tiers), clinical + popular-interest categories side by side, minimal single-section disclaimers, error-tolerant providers, and the GitHub-vs-NAS storage split with measured sizes. Remaining:

- **Which output categories ship first?** Aging clocks and robust-tier trait associations are the most defensible starting set. Speculative-tier findings can be included from the start (breadth is a goal) as long as the tier labeling is in place first.
- **Curated plain-language layer.** The raw databases speak in probe IDs and effect sizes. A curated marker → readable-sentence table is what turns that into 23andMe-style output; deciding its initial scope (how many markers, written by whom) is the main content question.
- **GDC strategy — resolved:** full local mirror. 294 GB fits on NVMe and downloads in under an hour on the 10 Gbit line, so there's no reason to accept live-through's first-run latency and cache-miss complexity for a static research snapshot. Live-through is reserved for genuinely-updating sources.
- **Repo location.** Confirm the target is the GoodAncestor private GitHub org as `methylask`; that sets where the ≤100 MB reference files get committed.
